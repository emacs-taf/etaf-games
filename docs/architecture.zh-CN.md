# ETAF 游戏应用开发契约

本文规定所有 ETAF 游戏应用必须遵守的职责、视觉、交互和验收要求。
它是接受标准，不表示所有应用已经满足这些要求；实际支持的行为以各游戏的
入口 Commentary 和用户手册为准。

## 工作区与框架边界

`etaf-games` 管理游戏应用、共同要求和集成检查。每款游戏位于同名子目录，
是拥有独立历史、入口、规则配置、资源、界面、测试和文档的仓库。
`etaf-gamekit` 继续作为独立游戏框架，不承载具体游戏或游戏启动菜单。

依赖方向为游戏应用 → GameKit / ETAF UI → ETAF。应用只使用各提供者根入口
声明的公共 API，不直接调用 Ebox，也不读取或修改后端、框架的私有状态。

| 所有者 | 职责 |
| --- | --- |
| 游戏应用 | 游戏身份、玩法配置、内容和资源、界面、局部交互状态、启动命令 |
| GameKit | 游戏定义、独立运行实例、通用后端适配、动作与观察结果、生命周期 |
| 原生游戏内核 | 规则、合法动作、回合或实时模拟、随机结果、世界状态和存档语义 |
| ETAF UI | 可跨应用复用的牌面、格子、按钮、面板等组件及视觉状态 |
| ETAF | 应用使用的组件、响应式状态、主题、布局和交互公共接口 |

添加游戏通常只增加应用代码。只有实际用例证明缺少通用能力时，才先在所属
提供者补能力，再由应用使用。不得把游戏名称、关卡、规则或专用开关混进框架。
通用组件按职责命名，不受第一款应用的名称或假设支配。

## 可玩的产品，不是接口演示

- 每款游戏提供完整的可玩回路：进入、操作、反馈、结束、重开和退出。
- 规则使用成熟内核时，前端不再实现第二份合法性、碰撞、计分或胜负判定。
  界面展示后端允许的操作；本地选择、提示面板等呈现状态由应用拥有。
- 明确注明规则变体、玩家模式、AI、撤销与存档的支持范围。内核目录里有一个
  游戏名，不等于它已有完整应用；支持规则也不等于已接入强 AI。
- 不用虚假的按钮、不可触发的控件或静态截图代替功能。未接入的能力不装作可用。
- 常用入口直接打开具体游戏，用户不需要先打开“引擎”或选择适配器。

## 视觉与亮暗双主题

每款游戏必须同时支持浅色和深色主题，采用同一套语义 token 和组件结构。
双主题是正常应用的基本能力，不是额外功能，也不因游戏类型而豁免。

- 两套主题分别设计背景层次、前景对比、强调色和状态色；不能只反转颜色。
  暗色主题不等于把所有区域铺成同一种灰暗色，浅色主题不能漏出暗色文字或面板。
- 牌面、棋子、地图、资源状态、按钮、浮层、选中、悬停、禁用和错误状态全部覆盖。
  颜色不作为区分阵营、花色或操作结果的唯一信息。
- 默认可跟随 Emacs 的亮暗外观，并提供可发现的手动切换入口。
  切换只更新呈现，保留实例、局面、选择、焦点、草稿和随机状态，不重启后端。
- 应用主题只影响自己的子树或 buffer，不修改用户的全局 Emacs 主题或其他应用。
- 使用现代、克制、统一的视觉语言：清晰的内容网格、层次、对齐和有意留白。
  不用大块空面板填满窗口，不用缩小正文或拉大图标掩盖布局问题。
- 可复用视觉能力先进入 ETAF UI。通用内容卡片和扑克牌具有不同职责，不能仅因
  名字都带“卡片”就混为一个带大量专用开关的组件。

## 游戏几何与自适应

游戏世界与周边界面分开适配。牌、格子、棋子和精灵的固有尺寸在不同窗口中
保持一致，不为了铺满宽度拉伸元素或改变棋盘、地图的比例。

宽度变化时，可以调整侧栏位置、面板排列、信息密度或把辅助功能收入面板；
高度变化时，优先去掉次要说明和多余间距，不挤压游戏元素或让控件互相覆盖。
内容必须有统一的行高预算，图标、花色和中文回退字体不能把标准行高撑大。

每款游戏根据可玩内容声明最小可用窗口。支持范围内的宽、普通、窄和矮窗口
都必须清晰且可操作；低于最小范围时保持结构，采用明确的裁切或滚动，不承诺
在极端尺寸里仍显示完整游戏。两套主题都使用相同的布局和几何规则。

## 输入、状态与生命周期

- 键盘和鼠标沿 ETAF 的公共输入路径工作，复用焦点、区域、帮助和控件导航。
  一个按键或一次激活只执行一次动作；局部选择立即反馈，后端响应异步发布。
- 保留框架的导航入口和 Emacs 原生中断。实时游戏的移动、发射等业务键与
  导航键有明确分工，焦点离开或暂停后不得残留持续操作。
- 状态高频更新只影响相关组件或保留节点，不重建整张界面。滚动、焦点、
  主题切换和窗口重排不能改变后端的权威局面。
- 每个实例独立拥有进程、计时器和请求；关闭、卸载或杀死 buffer 时释放资源。
  不关闭其他游戏或用户的 Emacs 进程。
- 非法动作、失败的读取和取消保留已接受状态，给出可读说明。存档显式执行，
  加载前验证候选内容，失败不破坏正在进行的游戏。

## 验收

每款游戏有自己的 `make check`、`tests/acceptance.json`、真实 GUI 场景和性能场景。
所有正确性场景只通过公共接口观察输入、结果、错误、回滚和生命周期。

| 门槛 | 必须验证的结果 |
| --- | --- |
| 独立使用 | 只依赖公共提供者，不依赖 GameKit 源码树中的应用目录或其他游戏 |
| 实际玩法 | 通过真实后端走通完整游戏回路，包含非法操作、重开、恢复和退出 |
| 双主题 | 相同局面在浅色、深色中均可读、美观；切换前后局面、焦点和实例不变 |
| 布局矩阵 | 宽、普通、窄、矮及低于最小范围的窗口；交互中调整尺寸后仍正确 |
| 输入 | 原生按键与 ETAF 焦点激活覆盖每个控件，不只从模型 API 改状态 |
| 性能 | 使用工作区统一测量工具，记录动作到可见更新；保留 GC 和慢样本 |
| 独立实例 | 同时运行的两局在局面、选择、主题、存档和关闭上互不影响 |

布局断言通过后仍须逐张查看截图。批处理通过不能代替 GUI 外观，后台 GUI
计时不能代替前台操作系统输入延迟。最终性能结论使用三组独立样本，每组至少
五次预热和三十次正式操作，并按场景预算和可比较基线判断；失败、缺失或旧代码
测量不能标记成通过。原始证据存放在版本库外。
